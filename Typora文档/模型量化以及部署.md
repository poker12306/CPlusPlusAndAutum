# 边缘设备量化部署 Playbook
### 以 `tensorrtx-yolov5-v6.0/yolov5` 为落地载体

> 本文目标：给定「一个模型 + 一个边缘设备」，回答三个问题
> 1. 从现在到上线，完整的流程框架是什么（有哪些阶段、每个阶段的 Gate 是什么）
> 2. 怎么**评估这个模型能不能在这个设备上跑**（用可测量的指标，不是猜）
> 3. 具体到**这份 yolov5 代码**，量化流程怎么走、每步动哪个文件、怎么验收

## 0. 先做路线选择 —— 这一步决定后面所有工作

这份代码**不是 ONNX 路线**。它用 TensorRT Network Definition API 在 C++ 里手搓网络
（`yolov5.cpp` + `common.hpp`），权重走 `.pt → .wts`（`gen_wts.py`），解码走自定义 plugin
（`yololayer.cu`）。这个架构决定了你的量化选项是被限定的：

| 路线 | 载体 | 量化方式 | 逐层精度控制 | QAT | DLA/NPU | 适用 |
|---|---|---|---|---|---|---|
| **A** | 本仓库 C++（手搭图） | 只有 **PTQ + 校准器** | 弱（`setPrecision` 是 hint） | ✗ | 部分 | 想保留这份代码，快速拿 INT8 |
| **B** | 从 ultralytics 导出 ONNX，用 `trtexec` / TRT Python 建 engine | PTQ + 校准器 / 逐 tensor dynamic range | 强 | ✓（QDQ） | ✓ | 精度不达标、要用 DLA、要上 TRT 10+ |
| **C** | ONNX + QAT（伪量化训练 → QDQ） | 训练时量化 | 最强 | ✓ | ✓ | 路线 A/B 精度都救不回来 |

**决策规则**

- 只要目标是「Jetson/Orin 上跑 yolov5，先要一个能用的 INT8 engine」→ **走 A**，见第 3 节。
- 出现下面任意一条，就必须离开 A 去 B/C：
  - 路线 A 量化后 mAP 掉超过可接受范围，且校准集/校准算法都优化过了；
  - 需要用 **DLA** 或设备上的 NPU（plugin 在 DLA 上不支持，必须把解码搬进图里）；
  - TensorRT ≥ 10（`IBuilder::setInt8Calibrator` / `IInt8EntropyCalibrator2` / 隐式 batch 已被移除）；
  - 需要**硬性地**指定"这几层必须 FP32"（路线 A 里 `setPrecision` 只是建议，见 §3.3 的说明）。

> 关键认知：**路线 A 的优势不是量化能力，而是"网络是我手搭的，我可以按模块粒度做精度开关和消融实验"**。
> 这是 ONNX 路线很难做到的（图被优化器重排过）。所以路线 A 最适合做的其实是
> **"敏感度扫描 + 定位该保住哪几层"**，然后把结论用到 B/C 上。

## 1. 通用框架：边缘端量化部署的 9 个阶段

```
 [0] 需求定义        latency/FPS · 功耗 · 内存预算 · 精度红线
      │
 [1] 设备能力探测     算力(TFLOPS/TFLOPS-INT8) · 带宽 · 显存 · 计算能力 · DLA/NPU · TRT/JetPack 版本
      │
 [2] 模型可行性评估    算子覆盖 · 内存预算 · roofline 时间上界 · 精度敏感层预判   ◀── Gate G1
      │
 [3] 图规范化          pt→wts / pt→ONNX · 固定 shape · BN 折叠 · 算子简化 · 后处理归属
      │
 [4] 基线建立          FP32 与 FP16 engine + 精度基线 + 延迟基线（没有基线就无法判断量化损失） ◀── Gate G2
      │
 [5] 量化策略选择      PTQ vs QAT · 校准算法 · 校准集构造 · 敏感层回退名单            ◀── Gate G3
      │
 [6] 量化执行          校准 → 建 engine → cache · 逐层精度报告
      │
 [7] 精度验收          端到端 mAP/指标 · 逐图 diff · 分层误差定位                     ◀── Gate G4
      │
 [8] 性能验收          延迟/吞吐 · 分层耗时 · 显存峰值 · 功耗/温度/降频               ◀── Gate G5
      │
 [9] 交付与回归        版本绑定 · cache 管理 · CI 回归 · 漂移监控
```

### 每阶段的产出与 Gate

| 阶段 | 产出物 | Gate（不通过就不往下走） | 不通过时回退到 |
|---|---|---|---|
| 1 设备探测 | 一张设备能力表（§2.1） | `platformHasFastInt8/Fp16` 明确；显存/带宽有数字 | 换设备 or 换精度目标 |
| 2 可行性 | 可行性结论表（§2.6） | 内存装得下 **且** roofline 时间上界 < 目标延迟 | 换模型变体/降分辨率/换设备 |
| 3 图规范化 | `.wts` 或 `.onnx` + 输入输出规格 | 输出张量语义明确（谁负责解码/NMS） | 调整后处理归属 |
| 4 基线 | FP32/FP16 engine + 精度数字 + 延迟数字 | 基线精度达标 | 先修模型/训练，别急着量化 |
| 5 策略 | 校准集 + 校准器 + 回退名单 | 校准集与推理预处理一致性自检通过（§3.2） | 重建校准集 |
| 6 量化执行 | INT8 engine + 逐层精度报告 | engine 里"看起来是 INT8"（§3.6） | 加大 workspace / 改校准器 |
| 7 精度验收 | 对比报告 | 精度降幅在红线内 | §5 决策树 |
| 8 性能验收 | 延迟/内存/功耗报告 | 达到目标 FPS 且不降频 | §5 决策树 |
| 9 交付 | 版本化产物 + 回归用例 | 可复现（同输入同引擎同结果） | 固化流程 |

> 工程上最常见的错误是**跳过阶段 4 直接量化**。没有基线，你无法区分"量化掉点"和"模型本来就烂"。

## 2. 阶段 1–2：怎么评估「这个模型能不能在这个设备上跑」

判断"能不能跑"有三个独立的门槛，**必须都过**。经验上边缘设备的失败顺序是：
**内存 > 算子支持 > 算力**（很多人一上来算 FLOPS，方向就错了）。

### 2.1 设备能力探测清单

必须拿到这些数字，写进一张表：

| 项目 | 怎么拿 | 对本项目的意义 |
|---|---|---|
| GPU 计算能力 (sm_XX) | `nvidia-smi --query-gpu=compute_cap --format=csv` / `deviceQuery` | sm ≥ 6.1 才有 DP4A；≥ 7.2 才有 INT8 Tensor Core |
| 是否支持 fast INT8 / FP16 | 小程序调 `builder->platformHasFastInt8()`、`platformHasFastFp16()`；或看 `yolov5.cpp` 运行日志 | 直接决定路线 A 能不能用（`yolov5.cpp:105` 有 `assert`） |
| DLA / NPU 是否存在 | Jetson: `cat /sys/devices/platform/*/…` / TRT 的 `platformHasDla()` | 有 DLA 就必须考虑路线 B（plugin 不支持 DLA） |
| 显存总量 & 可用 | `nvidia-smi`、`cudaMemGetInfo()`；Jetson 注意与 CPU 共享内存 | 见 §2.2 |
| 内存带宽 | 设备规格书（SoC 很多是 LPDDR，带宽是硬瓶颈） | roofline 的另一个上界，见 §2.3 |
| 计算能力峰值 (TFLOPS/TOPS) | 规格书 + 实测（用 `trtexec` 跑纯 conv 微基准） | §2.3 |
| TensorRT / CUDA / JetPack 版本 | `dpkg -l | grep nvinfer` / `python -c "import tensorrt;print(tensorrt.__version__)"` | 版本决定 API 可用性与 engine 可移植性 |
| 功耗/散热预算 | `tegrastats`(Jetson) / `nvidia-smi -q -d POWER` | 决定**稳态**帧率（不是峰值帧率） |

### 2.2 内存预算 —— 边缘端第一杀手

总需求 = 权重 + 激活峰值 + 运行时开销 + 框架开销。**逐项算清楚**：

**① 权重（随精度线性下降，这是量化最直接的收益）**

| | FP32 | FP16 | INT8(+scale) |
|---|---|---|---|
| yolov5n (1.9M) | 7.6 MB | 3.8 MB | ~1.9 MB |
| yolov5s (7.2M) | 28.8 MB | 14.4 MB | ~7.2 MB |
| yolov5m (21.2M) | 84.8 MB | 42.4 MB | ~21.2 MB |
| yolov5l (46.5M) | 186 MB | 93 MB | ~46.5 MB |
| yolov5x (86.7M) | 347 MB | 173 MB | ~87 MB |

**② 激活峰值（常常比权重还大，且量化收益有限）**

不要手算。用命令实测：

```bash
# 建 engine 时打开详细 profiling（需要在 yolov5.cpp 的 build 函数里加一行，见下）
trtexec --loadEngine=yolov5s.engine --plugins=./libmyplugins.so \
        --dumpLayerInfo --profilingVerbosity=detailed --verbose 2>&1 | grep -i "memory"
```

TRT 会打印 `Total Host Persistent Memory` / `Total Device Persistent Memory` /
**`Total Activation Memory`**，最后一项就是激活池峰值。

> 需要在 `yolov5.cpp` 的 `build_engine*()` 里加一行，否则 trtexec 拿不到层信息：
> ```cpp
> config->setProfilingVerbosity(ProfilingVerbosity::kDETAILED);
> ```

**③ 这份代码里两个容易被忽略的内存项（边缘设备上会要命）**

- `yolov5.cpp:16` + `378-380`：
  ```cpp
  #define MAX_IMAGE_INPUT_SIZE_THRESH 3000 * 3000
  cudaMallocHost((void**)&img_host,  MAX_IMAGE_INPUT_SIZE_THRESH * 3);  // 27 MB pinned host
  cudaMalloc    ((void**)&img_device, MAX_IMAGE_INPUT_SIZE_THRESH * 3);  // 27 MB device
  ```
  **固定申请 54 MB**（host pinned + device）只为放原图。你的实际输入如果是 640×640，改成
  `1280*1280` 甚至按实际最大图尺寸算，能省下几十 MB —— 在 2GB/4GB 的 Jetson 上是实质性的。
- CUDA context 本身在部分平台上要 200–500 MB。**评估"能不能跑"时一定要把它算进去**，这是新手最常翻车的地方。

### 2.3 算力/带宽 roofline：先算时间下界，再决定值不值得量化

```
T_compute = FLOPs / (Peak_TFLOPS × 有效利用率)      # 有效利用率边缘端 batch=1 常只有 10%~40%
T_memory  = 总访存字节 / 带宽
T_lower   = max(T_compute, T_memory)
```

参考 FLOPs（640×640，batch=1）：

| 模型 | Params | FLOPs |
|---|---|---|
| yolov5n | 1.9 M | 4.5 G |
| yolov5s | 7.2 M | 16.5 G |
| yolov5m | 21.2 M | 49.0 G |
| yolov5l | 46.5 M | 109.1 G |
| yolov5x | 86.7 M | 205.7 G |

**判断规则（经验值，非常重要）**

- 若 FP16 下的实测延迟已经接近目标 → 量化收益可能只有 1.1~1.5x，**不值得**付出精度代价。
- 若 FP16 下差 **1.5~2.5x** → INT8 通常能补上（边缘 SoC 有独立 INT8 单元时更明显）。
- 若 FP16 下差 **> 5x** → **不要先量化**，先换小模型变体（x→l→m→s→n）或降输入分辨率。
  量化最多给你 2x 左右，救不了 5x 的差距。这条能省掉你几周时间。
- **batch=1 是边缘端的常态**：桌面独显上 INT8 在 batch=1 时经常几乎不提速（瓶颈是访存和 kernel launch），
  而 Jetson/Orin 这类带专用 INT8 单元的 SoC 上收益明显。**别用桌面卡的结论去判断边缘设备。**

`总访存字节` 的估法：`Σ(每层输出张量字节数) + 权重字节数`，用
`trtexec --dumpLayerInfo` 导出的层输出尺寸求和即可。

### 2.4 算子覆盖率 —— 这份代码的实际盘点

对 `yolov5 v6.0` 这条手搭图，逐层对照（`common.hpp` / `yolov5.cpp` / `yololayer.cu`）：

| 代码位置 | 层 | INT8 可用 | 备注 |
|---|---|---|---|
| `common.hpp:164` `addConvolutionNd` | Conv | ✓ | 权重 per-channel 量化 |
| `common.hpp:154` `addScale` | BN 折叠后 | ✓ | 见下方"好消息" |
| `common.hpp:172` `addActivation(kSIGMOID)` | Sigmoid | ✓ | 实现为 LUT |
| `common.hpp:174` `addElementWise(kPROD)` | SiLU = x·σ(x) | ✓ | 输出动态范围大，是误差主要来源之一 |
| `common.hpp:194` `kSUM` | shortcut | ✓ | |
| `common.hpp:265-273` `addPoolingNd(kMAX)` | SPPF | ✓ | |
| `yolov5.cpp:62` `addResize(kNEAREST)` | 上采样 | ✓* | 个别 TRT 版本会退回 FP32，用 §3.6 确认 |
| `yolov5.cpp:68` `addConcatenation` | Concat | ✓ | |
| `common.hpp:323` `addPluginV2` | **YoloLayer_TRT** | **✗ 强制 FP32** | `yololayer.h:61-63` |

**好消息 1**：`yololayer.h:61-63` 的
```cpp
bool supportsFormatCombination(...) { return inOut[pos].format == kLINEAR && inOut[pos].type == kFLOAT; }
```
意味着 plugin **只接受 FP32**，TensorRT 必须在它前面插入 dequantize。所以
**"检测头解码"这一段天然是 FP32 的，不需要你做任何事**；反过来，plugin 也永远不可能 INT8 化。

**好消息 2**：`common.hpp:126-157` 的 `addBatchNorm2d` 在**加载 wts 时就用 FP32 把 BN 折叠成了 Scale 层的
scale/shift**（`gamma/sqrt(var+eps)`、`beta - mean*gamma/sqrt(var+eps)`）。也就是说
**BN 折叠发生在量化之前、且是精确 FP32 运算**，不会引入量化误差 —— 这在 ONNX 路线上是要专门处理的点。

**结论：这条网络的 INT8 算子覆盖率不是瓶颈。** 真正的瓶颈是
① 检测头（3 个 det conv）量化带来的精度损失；② SoC 上 INT8 单元的实际吞吐与访存。评估重点应放在这两处。

### 2.5 精度敏感度预判

先验判断（对 yolov5 普遍成立）：

| 部位 | 敏感度 | 原因 |
|---|---|---|
| 检测头 3 个 1×1 det conv + plugin 输入 | **高** | 输出直接决定 obj/cls 置信度；激活动态范围宽 |
| SiLU 输出（每个 convBlock 的尾巴） | 中高 | 无界输出，per-tensor 激活量化误差大 |
| SPPF 的 maxpool 输出 | 中 | max 会放大离群值 |
| backbone 浅层（model.0~model.2） | 低 | 特征值分布相对集中 |
| 深层 C3 | 中 | 通道数大，per-channel 权重量化缓解了大部分误差 |

所以**第一优先保护的是检测头**，这正好和 §3.3 的扫描策略对应。

### 2.6 可行性结论表（模板，填完再动手）

```

  激活峰值:  <trtexec 实测> MB          ← 关键数字
  运行时开销(CUDA ctx 等): ~<300> MB
  合计峰值:  <sum> MB   vs   可用 <MB>     → 装得下? Y/N

roofline(INT8):  T_compute=<ms>  T_memory=<ms>  T_lower=<ms>  vs 目标延迟 <ms>  → 够? Y/N

```

## 3. 基于这份 yolov5 代码的完整量化流程（路线 A）

每步都有**产出物**和**验收方式**。Step 0/1/2 是必须的；Step 3 是这份代码最大的价值所在。

### Step 0 · 建立基线（没有基线就没有验收标准）

```bash
# 1) pt → wts（FP32，与精度无关，只是权重搬运）
cp gen_wts.py {ultralytics}/yolov5 && cd {ultralytics}/yolov5
python gen_wts.py -w yolov5s.pt -o yolov5s.wts

# 2) 先建 FP32 基线 → 再建 FP16 基线
#    yolov5.cpp:11 改为 #define USE_FP32   → cmake .. && make → ./yolov5 -s ... s → 存为 yolov5s_fp32.engine
#    yolov5.cpp:11 改为 #define USE_FP16   → 重建                → 存为 yolov5s_fp16.engine
```

**验收**：两个 engine 用同一批 samples 跑 `-d`，框数/置信度一致或差异极小；
FP16 相对 FP32 的降幅就是你的"精度预算参考线"。

> 注意 `yolov5.cpp:11` 的宏是 `#if defined(USE_FP16) ... #elif defined(USE_INT8)`，**两个都定义 = 走 FP16**。

### Step 1 · 构造校准集（PTQ 成败的 70% 在这里）

要求：**500~1000 张**、**与线上同分布**、**覆盖所有场景/光照/尺度/类别**、**只放图片文件**。

```python
# tools/make_calib.py  —— 从训练/验证集抽样 + letterbox 到 640（与推理预处理对齐）
import cv2, os, glob, random, argparse
import numpy as np
ap = argparse.ArgumentParser()
ap.add_argument('--src', required=True)      # 原始图片目录（或若干目录）
ap.add_argument('--dst', required=True)      # 输出：yolov5/build/coco_calib
ap.add_argument('--n', type=int, default=800)
ap.add_argument('--size', type=int, default=640)
a = ap.parse_args()
os.makedirs(a.dst, exist_ok=True)
files = [f for d in a.src.split(',') for f in glob.glob(os.path.join(d, '**', '*.*'), recursive=True)]
files = [f for f in files if f.lower().endswith(('.jpg', '.jpeg', '.png', '.bmp'))]
random.seed(0); random.shuffle(files)
for i, f in enumerate(files[:a.n]):
    img = cv2.imread(f)
    if img is None: continue                      # 关键：坏图一定要跳过，不能写进目录
    r = min(a.size / img.shape[1], a.size / img.shape[0])
    nw, nh = int(round(img.shape[1] * r)), int(round(img.shape[0] * r))
    re = cv2.resize(img, (nw, nh), interpolation=cv2.INTER_LINEAR)
    out = np.full((a.size, a.size, 3), 128, np.uint8)   # 灰边 128，与 utils.h:24 / preprocess.cu:114 一致
    x, y = (a.size - nw) // 2, (a.size - nh) // 2
    out[y:y+nh, x:x+nw] = re
    cv2.imwrite(os.path.join(a.dst, f'{i:05d}.jpg'), out)
print('calib images:', len(os.listdir(a.dst)))
```

部署到运行目录（路径是**相对运行时 cwd** 的，`yolov5.cpp:107` 写的是 `"./coco_calib/"`）：

```bash
# 目录里只允许有图片文件！混入 .DS_Store / Thumbs.db / txt 会导致校准提前静默结束
cp -r coco_calib {tensorrtx}/yolov5/build/
find {tensorrtx}/yolov5/build/coco_calib -type f ! -name '*.jpg' -delete
```

**验收（一致性自检，必做）**：校准用的预处理必须与推理时的预处理**逐像素对齐**。这份代码两边是：

| | 校准路径 | 推理路径 |
|---|---|---|
| letterbox 填充值 | `utils.h:24` `Scalar(128,128,128)` | `preprocess.cu:114` `const_value_st = 128` |
| 归一化 | `calibrator.cpp:52` `1.0/255.0` | `preprocess.cu:74-76` `/255.0f` |
| 通道顺序 | `blobFromImages(..., swapRB=true)` | `preprocess.cu:69-71` BGR→RGB |
| 布局 | blobFromImages → NCHW | `preprocess.cu:79-85` RGBRGB→RRRGGGBBB |

自检方法：取一张图，分别过 `utils.h::preprocess_img` 和 CUDA `preprocess_kernel_img`，
转成同一布局后比 `max(abs(diff))`，应在 `~1/255` 量级（插值实现差异）。**两边不一致就一定会掉点**，
而且会表现成"换了校准集精度乱跳"这种难查的现象。

### Step 2 · 打开 INT8

需要改的地方（`yolov5.cpp`）：

1. **精度宏**（`:11`，两个 build 函数共用）
   ```cpp
   // #define USE_FP16
   #define USE_INT8
   ```
2. **workspace**（`:100` 与 `:204`）：`16 * (1 << 20)` → `1 << 30`。
   16 MB 在 INT8 下经常校准失败或选不到 INT8 kernel。TRT 8.4+ 可用
   `config->setMemoryPoolLimit(MemoryPoolType::kWORKSPACE, 1U << 30);`
3. **calibrator batch 与实际 batch 对齐**（`:107` 与 `:211`）
   ```cpp
   auto* calibrator = new Int8EntropyCalibrator2(BATCH_SIZE, INPUT_W, INPUT_H,
                                                 "./coco_calib/", "int8calib.table", INPUT_BLOB_NAME);
   ```
4. **校准缓存表**：首次构建生成 `int8calib.table`（在 cwd）。**改了网络结构/预处理/校准集后必须删除它**，
   否则复用旧 scale，精度会莫名其妙地掉。
5. **（建议）开逐层 profiling**，为后续验收做准备
   ```cpp
   config->setProfilingVerbosity(ProfilingVerbosity::kDETAILED);
   ```

构建与运行：

```bash
cd {tensorrtx}/yolov5 && mkdir -p build && cd build && cmake .. && make
sudo ./yolov5 -s yolov5s.wts yolov5s_int8.engine s     # 首次会遍历校准集，慢
sudo ./yolov5 -d yolov5s_int8.engine ../samples
```

> 推理端一行都不用改：`addInput` 传的是 `kFLOAT`、host 是 `float* buffers[]`
> （`yolov5.cpp:369-370`）、plugin 输出也是 `kFLOAT`。**换精度不影响宿主代码。**

### Step 3 · 敏感度分块扫描 —— 这份代码最大的杀手锏

因为网络是你在 C++ 里逐层搭的，`model.0 … model.23` 和 3 个 det conv 都是显式的 `ILayer*`，
所以你可以**按模块粒度做精度消融**，这是 ONNX 路线做不到的。

先加一个工具函数：

```cpp
// 把一个层的精度钉在 FP32
static void forceFP32(ILayer* l) {
    if (!l) return;
    l->setPrecision(DataType::kFLOAT);                  // hint
    for (int i = 0; i < l->getNbOutputs(); ++i) l->setOutputType(i, DataType::kFLOAT);
}
// 用法：forceFP32(det0); forceFP32(det1); forceFP32(det2);
```

扫描矩阵（每行建一个 engine，跑同一批验证图算 mAP）：

| 组 | 保留 FP32 的部分 | 目的 |
|---|---|---|
| G0 | 无（全 INT8） | 精度下界，看最大损失 |
| G1 | det0/1/2 + plugin 输入 | **验证"保护检测头"能救回多少**（通常是最划算的一步） |
| G2 | G1 + 所有 SiLU（`kPROD` 那些 `ew` 层） | 看宽动态范围激活的影响 |
| G3 | G2 + SPPF | |
| G4 | 只量化 backbone（head 全 FP32） | 精度上界，看"能接受多少" |
| G5 | 二分：逐个 C3 段回 FP32 | 精确定位敏感块 |

**关于这招的局限（必须知道）**：在 weakly-typed 模式下，`setPrecision(kFLOAT)` 只是 **hint**，
builder 可能为了性能忽略它。TRT 8.5+ 可以加
```cpp
config->setFlag(BuilderFlag::kPREFER_PRECISION_CONSTRAINTS);
```
让约束更硬。如果连这个都不被尊重 —— 那就是必须走路线 B（ONNX + 显式 Q/DQ）的明确信号，
因为只有 QDQ 能在图里**硬性**指定量化位置。

**产出**：一份"INT8 白名单/黑名单"（哪几段量化、哪几段保 FP32），以及精度-延迟的权衡曲线。

### Step 4 · 精度验收

```bash
# 逐层精度报告：确认哪些层真的跑在 INT8 上
trtexec --loadEngine=yolov5s_int8.engine --plugins=./libmyplugins.so \
        --dumpLayerInfo --profilingVerbosity=detailed 2>&1 | grep -iE "precision|int8|fp32"
```
（若 trtexec 对该 engine 的 batch 模式报错，就退回到用这份代码自带的
`inference time: xx ms`（`yolov5.cpp:405`）做延迟测量，用 `-d` 的输出图做精度对比。）

端到端对比要做三件事，缺一个都可能漏掉问题：

1. **同一批图跑 FP16 与 INT8，逐图 diff**：匹配框的类别/置信度差、框数差、IoU 分布。
   只看 mAP 会掩盖"个别图片全丢"这类严重问题。
2. **算 mAP**（COCO val 或你的验证集）。掉 1~3 个点是 PTQ-INT8 的正常范围；
   超过就要走 §5。
3. **分层误差定位**：对同一输入，比较 FP16/INT8 在**中间层输出**的余弦相似度与相对误差。
   这份代码里可以在 `common.hpp` 的分块函数（`C3`/`SPPF`/`convBlock`）返回处
   `markOutput` 出中间张量，用第 4 节那份两个 engine 的对比脚本读出来比 —— 直接定位到"第几段开始崩"。

### Step 5 · 性能验收

```bash
trtexec --loadEngine=yolov5s_int8.engine --plugins=./libmyplugins.so \
        --dumpProfile --dumpLayerInfo --iterations=200 --warmUp=1000
```
关注：**稳态**延迟（不是首帧）、P50/P99、分层耗时 Top-10、`Total Activation Memory`。
Jetson 上还要边跑边看 `tegrastats`（功耗、温度、是否降频）—— 边缘设备的"峰值帧率"没有意义。

**注意**：不要只看 `yolov5.cpp:405` 的 `inference time`，它**不包括预处理 kernel**
（`preprocess_kernel_img` 在计时区间外，见 `:398-403`）。在 640 分辨率下 CUDA 预处理通常占
整体 5~15%，边缘端占比更高。要做端到端计时就自己在外面加一圈计时。

### Step 6 · 交付与回归

- **engine 不可移植**：与 GPU 架构、TRT 版本强绑定。产物命名带上
  `model_precision_gpu_trtversion_hash`，例如 `yolov5s_int8_sm87_trt821_<hash>.engine`。
- **固化校准缓存**：`int8calib.table` 入库，保证同一个 engine 可复现；
  改任何东西先删表（§Step 2 第 4 条）。
- **CI 回归用例**：固定 20 张图 + 固定 mAP 阈值 + 固定延迟上限，engine 重建后自动跑。
- 精度红线一旦逼近，**立刻**开始准备路线 B/C，不要等到上线前。

## 4. 路线 B/C：什么时候必须离开这份代码，以及怎么衔接

**触发条件**（任一）：DLA/NPU 要用 · 需要 QAT · 需要硬性 Q/DQ 位置 · TRT ≥ 10 · 路线 A 精度救不回来。

**衔接要点（这里有坑）**：ultralytics 导出的 ONNX **已经把 Detect 解码放进图里了**，
输出形状和这份代码的 plugin 输出**完全不同**：

| | 路线 A（本代码） | 路线 B（ultralytics ONNX） |
|---|---|---|
| 输出 | `[1, 6001]`（`1 + 1000×6`，来自 plugin，`yololayer.cu:111-113`） | 如 `[1, 25200, 85]`（已解码的 xywh+obj+cls） |
| 解码 | `YoloLayer_TRT` plugin | 图内 |
| NMS | `common.hpp:59` CPU NMS | 需要 python/C++ 侧自己接（ultralytics 的 NMS 或 `EfficientNMS_TRT`） |
| 性能归属 | plugin 在 GPU 上跑 FP32 | 可全 INT8 |

所以切到路线 B **必须同时换掉后处理**，不能只换 engine。
如果只是想用 QAT 提升精度、但仍想用这份代码的 C++ 结构，可以把 ultralytics 的 QAT 模型导出为
**带 Q/DQ 的 ONNX**，用 TRT 建好 INT8 engine，然后自己写一个输出为 `[1,6001]` 的
decode 步骤（或保留 plugin 但改用显式 batch）；工作量比"全切路线 B"小。

其它要点：
- **QAT 路线**：PyTorch QAT（伪量化）→ 导出带 Q/DQ 的 ONNX → TRT 直接吃 scale，**不需要校准集**，
  精度通常明显好于 PTQ。这是精度不达标时的正解。
- **DLA**：plugin 不支持 DLA，Yolo 层会回落到 GPU；且 DLA 对某些层/格式有限制，需要
  `--dumpLayerInfo` 确认真实分配。DLA 上更推荐"解码进图"的 ONNX 路线。
- **TRT 10+**：`setInt8Calibrator`/`IInt8EntropyCalibrator2`/隐式 batch 全部移除，
  路线 A 直接不可用；必须走显式 batch + 强类型/`ICastLayer`/QDQ。

## 5. 失败模式 → 决策树

```
G1 平台不支持 INT8 (platformHasFastInt8=false)
   ├─ 确认 sm ≥ 6.1；Jetson 上确认 JetPack/TRT 版本
   ├─ 用 FP16（yolov5 上 FP16 掉点通常 <0.5 点，是性价比最高的选择）
   └─ 有 DLA/NPU → 路线 B

G4 精度掉太多
   ├─ 1. 校准集：数量 ≥500？分布对齐线上？目录里无非图片文件？     ← 80% 的问题在这
   ├─ 2. 一致性自检：校准预处理 == 推理预处理？（§Step 1 验收）
   ├─ 3. 换校准算法：EntropyCalibrator2 ←→ IInt8MinMaxCalibrator（检测网常推荐 MinMax），删表重建
   ├─ 4. 敏感度扫描：把 det0/1/2（和/或 SiLU）回 FP32        ← 通常最划算
   ├─ 5. 加 kPREFER_PRECISION_CONSTRAINTS（TRT 8.5+）
   └─ 6. 还不行 → QAT（路线 C）

G5 速度没变快 / 变慢
   ├─ 1. --dumpLayerInfo 确认真的跑在 INT8（可能大量层回落 FP32）
   ├─ 2. workspace 太小 → 选不到 INT8 kernel（16MB → 1GB）
   ├─ 3. batch=1 在桌面卡上本来就没收益 → 回到 §2.3 判断规则，别硬做
   ├─ 4. 端到端没快：预处理/后处理成了瓶颈（plugin FP32 解码 + CPU NMS）
   └─ 5. 降频：Jetson 上看 tegrastats，功耗墙到了就不会更快

内存不够
   ├─ 1. 收紧 MAX_IMAGE_INPUT_SIZE_THRESH（27MB×2 的固定开销，yolov5.cpp:16,378-380）
   ├─ 2. 换小变体 / 降输入分辨率（收益远大于量化）
   └─ 3. 确认 CUDA context 开销已计入
```
