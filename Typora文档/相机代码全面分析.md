## 1. 项目全局概览 (Project Overview)

### 1.1 业务场景与核心功能

这是一个运行在无人驾驶卡车（或远程遥控车辆）上的 **前视相机感知节点**：从 USB/V4L2 相机取流，在 Jetson 上以 TensorRT 加速运行 YOLOv5 检测，叠加 ByteTrack 多目标跟踪、自车转向角联动的动态 ROI 过滤、镜头遮挡检测与传感器健康状态聚合，最终以两条路径输出——一路是给整车其他模块消费的 **JSON 结构化目标列表**（经 dora 框架发布），另一路是 **叠加了 HUD 的 H.264/RTMP 实时视频流**推送到云端供远程驾驶舱监看。

核心功能可拆为五件事：**检测 → 跟踪 → 空间过滤 → 健康自检 → 双路输出**。

### 1.2 核心数据流向

```
[输入层]
  /dev/video10 (V4L2 UVC)  ──┐
  dora timer tick (20ms)   ──┤
  VehicleStatus  话题        │   ← 车速 / 转向角
  lidar_fault_zvision1~5    │   ← 5 路激光雷达故障码
  gnss_fault      话题       │   ← GNSS 故障码
                             ▼
┌─────────────────────────────────────────────────────────────────────┐
│ 主线程 (dora event loop, 单线程串行执行整条感知链)                    │
│                                                                       │
│  cap_ >> frame_            (OpenCV V4L2 同步取流)                     │
│         │                                                             │
│         ├──► occlusion_detector_->pushFrame()  ──► [独立线程] 遮挡检测 │
│         │                                          Sobel+时域稳定性   │

│    ├─ memcpy → pinned host buffer  ★CPU 侧第三份拷贝                  │
│    └─ doInference:  cudaMemcpyAsync H2D → context.enqueue             │
│                     → cudaMemcpyAsync D2H → cudaStreamSynchronize     │
│         │                                                             │
│         ▼                                                             │
│  CPU 后处理: nms() (按类别分组 + 贪心 IoU 抑制)                        │
│             → 逐类别 decode + 单目测距 estimateDistance()             │
│             → std::vector<bounding_box>                               │
│         │                                                             │
│         ▼                                                             │
│  ByteTrack: Object[] → tracker_.update() → STrack[]                   │
│    (卡尔曼预测 → 匈牙利/lapjv 两级关联(高/低分) → 轨迹生命周期管理)      │
│         │                                                             │
│         ▼                                                             │
│  IoU 反向关联: 用 STrack 框去原始 detections 里找 class_id / distance   │
│         │                                                             │
│         ▼                                                             │
│  阿克曼转向二次曲线 → ego_lane_polygon → 底边 3 点采样 → ROI 过滤      │
│         │                                                             │
│         ├──► JSON(5位ASCII长度前缀 + body) → dora_send_output          │
│         │      topic: camera_msg                                      │
│         ▼                                                             │
```

**关键事实：整条感知链（取流、推理、跟踪、绘制、序列化）全部压在 dora 主线程上，完全串行。** 只有「遮挡检测」和「RTMP 编码推流」跑在独立线程。

## 2. 核心技术栈与依赖 (Tech Stack)

### 2.1 语言与 C++ 特性

构建标准为 C++17（[CMakeLists.txt:3](CMakeLists.txt#L3) `-std=c++17`）。

### 2.3 值得注意的版本锁定信号

[macros.h](include/Detect/macros.h) 中 `NV_TENSORRT_MAJOR >= 8` 条件编译 `TRT_NOEXCEPT`/`TRT_CONST_ENQUEUE`，说明代码需要兼容 TRT 7 与 8。但：

- [yolov5.cpp:510](src/Dedect/yolov5.cpp#L510) 使用 `context.enqueue(...)`（TRT 8.5 起废弃，TRT 9 移除）
- [yolov5.cpp:598](src/Dedect/yolov5.cpp#L598) 使用 `getBindingIndex`（TRT 8.5 废弃，TRT 10 移除）
- [yolov5.cpp:417](src/Dedect/yolov5.cpp#L417) `createNetworkV2(0U)` + `builder->setMaxBatchSize` + `config->setMaxWorkspaceSize`（TRT 8 废弃，TRT 9 移除）
- 而 [Gemini.cpp:142](src/Dedect/Gemini.cpp#L142) 用的是较新的 `enqueueV2`

**结论：实际锁定在 TensorRT ≤ 8.4 区间。** 这是面试中「你的代码如何做 TRT 版本演进」的天然切入点。

### 3.2 单一职责分析

**做得好的部分：**

| 模块 | 职责 | 边界清晰度 |
|---|---|---|
| `PushRTMP` | 只做 `BGR → YUV420P → H.264 → FLV → RTMP` | ★★★★ 高。不感知业务，接口只有 `initRTMP` / `startPush` |
| `KalmanFilter` | 纯数学，无任何业务状态 | ★★★★★ 高。可独立单测 |
| `lapjv` | 纯算法，`int_t/cost_t` 类型隔离 | ★★★★★ 高。源自 scipy 的 C 移植 |
| `RobustOcclusionDetector` | 自持线程 + 队列 + 算法，对外只暴露 `pushFrame` / `getLatestOcclusionRate` | ★★★★ 高 |
| `Yolov8Detector` | 把 TRT 生命周期、预处理、后处理、测距全封装在类内，RAII 释放 | ★★★★★ 高。**这才是正确的 OOP 形态** |

**职责越界 / 待改进的部分：**

1. **`Yolov5` 模块是「函数 + 全局变量」风格**，而非类。`runtime`/`engine`/`context`/`buffers[2]`/`host_input_data`/`host_output_prob`/`stream` 全部是 [yolov5.cpp:33-46](src/Dedect/yolov5.cpp#L33) 的**文件级全局变量（外部链接）**。这意味着：
   - 整个进程只能有一个检测器实例，无法做多路相机
   - 无法并发调用（TRT `IExecutionContext` 本身也不是线程安全的）
   - 头文件只暴露 `yolo_main()`/`engine_init()` 这种隐式单例接口

   对比 [Gemini.h](include/Detect/Gemini.h) 的 `Yolov8Detector` 类——它做了完全相同的事，但用类成员 + `= delete` 拷贝 + RAII 析构。**仓库里同时存在这两套实现，风格割裂。** 这是一个非常好的架构演进叙事素材。

2. **`Camera_dora_node` 严重超载**。它的成员变量覆盖了：配置项、相机句柄、引擎路径、HTTP 客户端参数、ROI 几何参数、传感器状态机（6 路 + 超时）、模糊滤波参数（`history_bboxes_`/`HISTORY_SIZE`/`MIN_APPEARANCES`/`IOU_THRESH`，**全部未使用**）。`CameraCallback` 单函数 325 行，同时做了：遮挡推送、推理调用、坐标格式转换、跟踪调用、类别反查、动态 ROI 生成、多边形填充绘制、逐目标 ROI 采样过滤、渲染、JSON 构造、推流推送。

   其中 [.cpp:94-97](include/Camera_dora_node.hpp#L94) 的 `history_bboxes_`（`std::deque<std::vector<bounding_box>>`）连同 `HISTORY_SIZE`/`MIN_APPEARANCES`/`IOU_THRESH` 三个常量**声明了但从未被任何函数读写**——是已被 ByteTrack 取代的旧滤波逻辑残留。

3. **`draw_hud` 被放在推流器里，但它其实是业务层的展示逻辑**（要读车速、要读 6 路传感器状态）。这让 `UsbCameraStreamer` 从「纯粹的视频通道」变成了「业务 HUD 渲染器」，耦合了 `VehicleSensorState` 结构。

### 3.3 核心模块间的交互方式

| 交互对 | 机制 | 方向 | 同步原语 |
|---|---|---|---|
| dora 框架 ↔ 节点 | **事件驱动 + 回调分发**：`dora_next_event()` 阻塞取事件，按 topic id 字符串 `strncmp` 分派 | 双向 | 无（单线程内） |
| `Camera_dora_node` → `RobustOcclusionDetector` | **有界队列 + 条件变量**（生产者-消费者） | 单向异步 | `mutex_` + `cv_`，队列满丢最旧 |
| `Camera_dora_node` → `UsbCameraStreamer` | **有界队列 + 条件变量** | 单向异步 | `_mutex` + `conv`，队列满丢最旧 |
| `Camera_dora_node` → `UsbCameraStreamer`（状态） | **结构体整体拷贝**（值传递），非队列 | 单向 | `state_mutex_` |
| `Camera_dora_node` → dora → 下游 | **共享内存/序列化消息**：`dora_send_output(ctx, topic, data, len)` | 单向 | 框架内部 |
| `VehicleStatusCallback` → 遮挡检测器 | **`std::atomic<float>` 无锁写** | 单向 | 无锁 |
| 遮挡检测器 → 节点 | **`std::atomic<double>` 无锁读** | 单向 | 无锁 |
| `Yolov5` 模块 ↔ 节点 | **全局变量隐式共享**（非显式接口） | — | **无任何保护** |
| `ByteTrack` ↔ 节点 | **值返回** `std::vector<STrack>` | 单向 | 无（仅主线程访问） |

**两种队列的「丢帧策略」值得注意**：`frame_queue_.size() >= max_queue_size_` 时 `pop()` 再 `push()`——**丢最旧、保最新**。这对实时感知是正确的选择（宁可丢帧也不能让延迟累积），比「阻塞生产者」或「丢最新」都更适合车载场景。

## 4. 核心业务逻辑走读 (Core Logic Flow)

### 4.1 启动生命周期

```
main()                                   [main.cpp:5]
 └─ Camera_dora_node 构造
     ├─ to_exit_processing_ = false
     └─ dora_context_ = init_dora_context_from_env()   ← 失败仅打印错误，不中断
 └─ camera_dora_node.run()               [.cpp:640]
     ├─ init()                           [.cpp:116]
     │   ├─ 读环境变量 CONFIG_PATH，回退到硬编码绝对路径
     │   ├─ YAML::LoadFile → 解析 15 个配置项（均带默认值）
     │   ├─ engine_init(engine_path_)     ← TensorRT 全套初始化
     │   ├─ Push_Rtmp_Init()              ← HTTP 查推流地址（3 次重试）
     │   ├─ cap_.open(camera_index_, cv::CAP_V4L2)
     │   ├─ 若网络 OK → new UsbCameraStreamer + startStreaming()
     │   └─ occlusion_detector_ = make_unique<...>(...) + start()
     └─ while(!to_exit_processing_) { dora_next_event → 按 topic 分派 }
```

**`init()` 的错误处理是致命的**：函数返回 `void`，任何一步失败（配置文件缺失、引擎加载失败、相机打不开）都是 `return;`——**直接返回，但 `run()` 并不知道失败，依然进入事件循环。**

### 4.2 模型加载与反序列化（Engine）

```cpp
bool engine_init(std::string engine_name)        // [yolov5.cpp:548]
{
    cudaSetDevice(DEVICE);                       // 绑定 GPU 0
    file.seekg(0, file.end); size = file.tellg();
    trtModelStream = new char[size];             // 堆分配引擎 blob
    file.read(trtModelStream, size);             // 一次性读入内存
    file.close();                                // 尽早关闭文件句柄

    runtime = createInferRuntime(gLogger);       // ① 创建运行时
    engine  = runtime->deserializeCudaEngine(trtModelStream, size);  // ② 反序列化
    delete[] trtModelStream;                     // ③ 立即释放 blob ★
    context = engine->createExecutionContext();  // ④ 创建执行上下文

    if (engine->getNbBindings() != 2) return false;              // ⑤ 校验绑定数
    inputIndex  = engine->getBindingIndex("data");
    outputIndex = engine->getBindingIndex("prob");
    if (inputIndex != 0 || outputIndex != 1) return false;       // ⑥ 校验绑定顺序

    // ⑦ 一次性分配全部 GPU/CPU 资源
    cudaMalloc(&buffers[0], 1*3*640*640*4);      // 输入显存 ≈ 4.9 MB
    cudaMalloc(&buffers[1], 1*6001*4);           // 输出显存 ≈ 24 KB
    cudaMallocHost(&host_input_data,  ...);      // ★ 锁页内存 4.9 MB
    cudaMallocHost(&host_output_prob, ...);      // ★ 锁页内存 24 KB
    cudaStreamCreate(&stream);                   // ★ 专用 CUDA 流
}
```

**几个值得点出的细节：**

- **第 ③ 步的 `delete[] trtModelStream` 是关键优化**。`deserializeCudaEngine` 完成后，TensorRT 内部已经把权重搬进了自己的显存/内存结构，host 侧的 16 MB blob 不再需要。原版 trtx 样例常把它泄漏掉。注释 [yolov5.cpp:591](src/Dedect/yolov5.cpp#L591) 保留了被删掉的那行 `// delete[] trtModelStream;`，说明这是有意为之的修复。
- **自定义插件必须在 `deserializeCudaEngine` 之前完成注册**。`YoloLayerPlugin` 通过 `REGISTER_TENSORRT_PLUGIN(YoloPluginCreator)` 静态注册（[yololayer.h:135](include/Detect/yololayer.h#L135)），而这行宏在 `myplugins.so` 里。因为整段推理代码**没有引用 `myplugins` 的任何符号**，只靠 `target_link_libraries(... myplugins)` 链接——在 Ubuntu 默认 `-Wl,--as-needed` 下，共享库若未被引用会被链接器**丢弃 DT_NEEDED 项**，导致运行时插件找不到、`deserializeCudaEngine` 返回 nullptr。这是这类工程踩过的经典坑。
- **反序列化时 `CLASS_NUM` 与 `MAX_OUTPUT_BBOX_COUNT` 由引擎自带**（`YoloLayerPlugin::YoloLayerPlugin(const void*, size_t)` 从字节流 `read`），而 host 侧的 `OUTPUT_SIZE` 却是编译期从 [yololayer.h:19-20](include/Detect/yololayer.h#L19) 算出来的 `1000*6+1`。**两者必须一致，否则 D2H 拷贝长度错误**。代码里没有任何运行期校验。

### 4.3 单帧推理路径


**测距模型**是标准单目针孔：`Z = (W_real × f) / w_pixel`。`f` 从配置读（`g_focal_length`），`W_real` 按类别给常量（人 1.7 m、车/卡车高度、杆件宽度）。

### 4.4 TensorRT 插件内部（GPU 端解码）

[yololayer.cu:182-234](include/Detect/yololayer.cu#L182) 的 `CalDetection` kernel：

```
每个线程处理一个 grid cell：
  1. Logist(conf) < IGNORE_THRESH(0.1) → 直接 return（early-exit 省掉后续分类循环）
  2. 遍历 classes 找 argmax（class score）
  3. atomicAdd(res_count, 1) 原子抢占输出槽位 —— ★ 天然去重、无锁并发写入
       count >= maxoutobject → return（防止溢出固定长度输出缓冲）
  4. 解码:
       cx = (col - 0.5 + 2·sigmoid(tx)) · netW / gridW
       cy = (row - 0.5 + 2·sigmoid(ty)) · netH / gridH
       w  = (2·sigmoid(tw))² · anchor_w
       h  = (2·sigmoid(th))² · anchor_h
  5. conf = box_prob × cls_prob
```

输出布局是 `[count, Detection, Detection, ...]`，`Detection` 为 24 字节（4 bbox + conf + class_id）。**这是把后处理的 decode 部分下沉到 GPU 的典型做法**，主机侧只剩 NMS。

`forwardGpu` 里用 `cudaMemsetAsync` 清零每个 batch 的 count 字段，三个尺度（80×80/40×40/20×20）各 launch 一次 kernel，**全部挂到同一个 stream 上保持顺序**。

### 4.5 多目标跟踪的接入点

接入在 [Camera_dora_node.cpp:211-226](src/Camera_dora_node.cpp#L211)：


`BYTETracker::update()` 内部是标准的 BYTE 两级关联状态机（[BYTETracker.cpp:19-241](src/Track/BYTETracker.cpp#L19)）：

| 步骤 | 动作 | 关键参数 |
|---|---|---|
| Step 1 | 按分数把检测分成高分桶 / 低分桶 | `track_thresh = 0.2` |
| Step 2 | 高分框 × (已激活轨迹 ∪ 丢失轨迹)，**卡尔曼预测后**算 IoU 代价 → lapjv 分配 | `match_thresh = 0.7` |
| Step 3 | 剩余轨迹 × 低分框，二次关联（BYTE 的核心思想：低分框也可能是真目标） | 阈值 0.5 |
| Step 4 | 未确认轨迹（只有 1 帧历史）与剩余高分框关联，仍匹配不上则删除 | 阈值 0.7 |
| Step 5 | 未匹配高分框且 `score ≥ high_thresh(0.7)` 才新建轨迹；超时未更新的丢失轨迹删除 | `max_time_lost = 30/30*30 = 30` 帧 |

**跟踪的入参配置存在明显不一致**：`BYTETracker tracker_{30,30}` 传入了 `frame_rate=30, track_buffer=30`，但构造函数 [BYTETracker.cpp:4-13](src/Track/BYTETracker.cpp#L4) **完全忽略了这两个参数**（只用它们算了一个 `max_time_lost`），三个阈值全是硬编码。头文件默认参数给人的「可配置」印象是假的。

### 4.6 跟踪框 → 类别的反向关联

BYTE 的 `STrack` 只保留 `tlwh` 和 `score`，**不携带类别信息**。为了给下游输出类别和距离，代码用了一个 IoU 反查（[.cpp:296-310](src/Camera_dora_node.cpp#L296)）：

```cpp
for (const auto& strack : output_stracks) {
    cv::Rect_<float> trk_rect(tlwh[0], tlwh[1], tlwh[2], tlwh[3]);
    float max_iou = 0.0;
    for (const auto& raw_b : raw_bboxes) {            // O(T × D) 双重循环
        float iou = (trk_rect & det_rect).area() / ((trk_rect | det_rect).area() + 1e-5);
        if (iou > max_iou) { max_iou = iou; best_class_id = ...; best_distance = ...; }
    }
    // 注意：没有对 max_iou 设下限，max_iou==0 时也会采用最后一个遍历到的框的类别
}
```

**这是"想当然"的补救措施，存在明确缺陷**：跟踪框是卡尔曼平滑/预测后的结果，当目标被遮挡或漏检时，跟踪框可能和任何当前检测框都不重叠（`max_iou == 0`），此时 `best_class_id` 会停留在 `raw_bboxes` 中最后一个参与比较的框的类别——**即随机赋值一个错误类别**。更正确的做法是让 `STrack` 携带 `class_id`（在 `update()` 里继承检测的类别），而不是事后反查。

### 4.7 多线程同步与互斥逻辑详解

**线程清单（推断 3 个业务线程 + 库内部线程池）：**

| 线程 | 归属 | 循环 | 退出条件 |
|---|---|---|---|
| **主线程** | dora event loop | `while(!to_exit_processing_)` | dora Stop 事件 / 意外事件 |
| **遮挡检测线程** | `RobustOcclusionDetector::workerLoop` | `while(true)` | `!is_running_ && frame_queue_.empty()` ✅ 可退出 |
| **推流线程** | `UsbCameraStreamer::streamingFunction` | `while(true)` | **无退出条件** ❌ 见 §6.3 |

**遮挡检测器的三把锁设计（有亮点也有问题）：**


拆锁的意图很清楚：**把「热路径的标量读取」和「慢速配置修改」解耦**。`getLatestOcclusionRate()` 走原子读，不碰任何锁；`setNeutralExclusionThreshold()` 才会去抢 `config_mutex_` 并清空缓冲。

`process()` 里的参数快照也是标准做法——先在 `config_mutex_` 保护下把 4 个参数拷到局部变量（[.cpp:57-66](src/Occlusion/RobustOcclusionDetector.cpp#L57)），**然后释放配置锁再做重活**，避免长时间持锁阻塞配置变更。

**但 `process()` 里的 `mutex_` 是致命伤**（[.cpp:128](src/Occlusion/RobustOcclusionDetector.cpp#L128)）：

```cpp

m_accumulated_mask += mask_01;
m_mask_buffer.push_back(mask_01.clone());
...

```

**这意味着：主线程的 `CameraCallback → occlusion_detector_->pushFrame() → lock(mutex_)` 会被工作线程的整段图像处理阻塞。** 工作线程的存在本意是卸载主线程，但因为锁粒度过大，主线程实际上是在同步等待遮挡检测算完。详见 §6.2。

**传感器状态机的同步**：`current_node_state_`（`VehicleSensorState`）只在主线程被读写（全部回调都在 event loop 里执行），**无需加锁**——这是正确的判断。它通过 `syncSensorStateToStreamer()` 整体拷贝进 `UsbCameraStreamer`，由 `state_mutex_` 保护。两个 `VehicleSensorState` 副本（Node 一份、Streamer 一份）是典型的「快照同步」模式。

## 5. 工程化与性能亮点提炼 (Engineering Highlights)

### 5.1 显存/内存生命周期管理

**亮点 1 — 全部 GPU 资源在 `engine_init` 一次性分配，运行期零分配零释放**

[yolov5.cpp:605-615](src/Dedect/yolov5.cpp#L605) 的注释 `// ================== GPU 显存优化 ==================` 是作者明确的意图标记。对比原版 trtx 样例（每帧 `cudaMalloc`/`cudaFree`），这里做了三件事：

```cpp
cudaMalloc(&buffers[inputIndex],  ...);   // 输入显存，一次
cudaMalloc(&buffers[outputIndex], ...);   // 输出显存，一次
cudaMallocHost(&host_input_data,  ...);   // ★ 锁页内存
cudaMallocHost(&host_output_prob, ...);   // ★ 锁页内存
cudaStreamCreate(&stream);                // 专用流
```

**`cudaMalloc`/`cudaFree` 是全局同步操作**（会隐式 device synchronize），每帧调用会让 GPU 空转数十微秒到毫秒级。消除运行期分配是这个模块最重要的性能改进。

**亮点 2 — 锁页内存 (Pinned Memory) 的引入**

`cudaMallocHost` 分配的是**页锁定内存**，DMA 引擎可以直接访问而无需 CPU 参与换页。相比可分页内存（pageable），`cudaMemcpyAsync` 在 pinned 内存上：
- 是**真正的异步**（pageable 内存的 async 拷贝往往退化为同步拷贝）
- 带宽可提升 2~3 倍（Jetson 上 H2D 典型 6–12 GB/s @ pinned vs 2–4 GB/s @ pageable）

每帧要传 640×640×3×4 = **4.9 MB** 到 GPU，27 fps 下是 **133 MB/s** 的持续带宽需求，pinned 内存的收益是实打实的。

**亮点 3 — `engine_release()` 的幂等清理 + 空指针归位**

```cpp
void engine_release() {          // [yolov5.cpp:841]
    if (stream) { cudaStreamDestroy(stream); stream = nullptr; }
    if (buffers[0]) { cudaFree(buffers[0]); buffers[0] = nullptr; }
    ...
    if (context) { context->destroy(); context = nullptr; }
    if (engine)  { engine->destroy();  engine  = nullptr; }
    if (runtime) { runtime->destroy(); runtime = nullptr; }
}
```

每个指针释放后立刻置空，函数可由 `~Camera_dora_node()` 安全重复调用。**释放顺序也是正确的**：先销毁 stream（无 pending 工作），再释放 buffer，最后按 `context → engine → runtime` 的反向依赖顺序销毁 TRT 对象（销毁 runtime 前必须先销毁其创建的所有对象）。

### 5.2 并发与队列设计

**亮点 4 — 有界队列 + 丢最旧策略（背压管理）**

```cpp
void pushFrame(const cv::Mat& frame_bgr) {
    std::lock_guard<std::mutex> lock(mutex_);
    if (frame_queue_.size() >= max_queue_size_) {
        frame_queue_.pop();          // ★ 丢最旧，而非丢最新或阻塞
    }
    frame_queue_.push(frame_bgr.clone());
    cv_.notify_one();
}
```

`max_queue_size_ = 2`（遮挡）/ `= 5`（推流）。这个策略对实时系统是正确的：**宁可丢帧，也不让端到端延迟随时间累积**。如果换成阻塞生产者，主线程会被推流线程拖垮；如果换成 `if full then drop new`，则消费端永远处理的是陈旧帧。

**亮点 5 — 无锁标量传递**

高频读、低频写、且读写无复合依赖的标量，用 `std::atomic<T>` 而不是加锁：

```cpp
std::atomic<double> latest_occlusion_rate_{0.0};
double getLatestOcclusionRate() const { return latest_occlusion_rate_.load(std::memory_order_relaxed); }
```

`memory_order_relaxed` 的选择也是对的——这个值不需要与其他内存操作建立 happens-before 关系，只要能读到「某个新近值」即可。

**亮点 6 — 锁的分层**（设计意图正确，实现有缺陷，见 §6.2）

`config_mutex_`（配置）/ `mutex_`（数据）/ `mask_mutex_`（输出）三把独立锁，配合 `process()` 开头的参数快照，意图是把锁的持有时长压到最短。配置锁只在 `setXxx()` 和参数快照处使用，不参与热路径。


**亮点 10 — 阿克曼转向联动的动态 ROI**

[.cpp:236-285](src/Camera_dora_node.cpp#L236) 是本项目最有业务深度的算法段。它把底盘下发的转向角转成一个随距离平方（实际代码是三次方 `t*t*t`）增长的横向偏移，生成左右两条贝塞尔式车道曲线，再首尾相连成闭合多边形：

```cpp
const float CURVE_SCALE_FACTOR = 20.0f;
for (int i = 0; i <= NUM_PTS; ++i) {
    float t = i / NUM_PTS;                       // 0=最近端(画面底部 y=1080), 1=最远端(y=600)
    float current_y = 1080.0f - t * (1080.0f - 600.0f);
    float base_x_left  = leftdown_ + t * (leftup_  - leftdown_);
    float base_x_right = rightdown_ + t * (rightup_ - rightdown_);
    float delta_x = current_steering * CURVE_SCALE_FACTOR * (t * t * t);  // 近端几乎不动，远端大幅偏移
    left_curve.push_back(cv::Point(base_x_left + delta_x, current_y));
    right_curve.push_back(cv::Point(base_x_right + delta_x, current_y));
}
// 右侧曲线反向遍历才能闭合多边形
for (auto it = right_curve.rbegin(); it != right_curve.rend(); ++it)
    ego_lane_polygon.push_back(*it);
```

这个 ROI 有双重作用：**(1)** 画在画面上作为可视化；**(2)** 用 `cv::pointPolygonTest` 过滤掉不在本车道内的卡车/自行车/摩托车/交通标志（[.cpp:342-357](src/Camera_dora_node.cpp#L342)）。逻辑是「目标框底边的 3 个采样点只要有 1 个落在 ROI 内就保留」——**保守策略防止加塞漏检**。

`leftup_/leftdown_/rightup_/rightdown_` 从 YAML 配置读取，是标定后的 ROI 梯形四角。

## 6. 面试「高频追问」预警 (Interview Deep-Dive Warnings)

> 以下每一点都是代码里**真实存在**的问题，且都是大厂面试官看到这份代码后最可能追问的方向。按「被问到的概率 × 严重程度」排序。

### 6.1 【最高危】`exit(1)` 作为延迟看门狗 —— 单帧抖动即整机崩溃

**代码位置**：[yolov5.cpp:657-660](src/Dedect/yolov5.cpp#L657)

```cpp
if(std::chrono::duration_cast<std::chrono::milliseconds>(end - start).count() > 150)
{
    exit(1);
}
```

**问题**：在推理热路径上用 `exit(1)` 终结进程，用来「防止延迟过大」。

**为什么这是灾难性的**：
1. **`exit(1)` ≠ 优雅退出**。它只运行已注册的 `atexit`/静态析构，**不会**执行 `engine_release()`（那是 `~Camera_dora_node` 里调的，而 `exit()` 不会展开栈、不会调用局部对象的析构）。CUDA 上下文、TRT 对象全部泄漏——不过进程都要死了，这倒是次要的。
2. **触发条件是「延迟 > 150ms」，而不是「持续不可用」**。Jetson 上任何一次的 CPU 抢占、内存带宽争抢（比如 x264 的 16 线程正在抢带宽）、Linux 页回收、GPU 时钟门控，都可能让**单帧**超过 150ms。**代价是整个卡车感知节点重启。**
3. **重启意味着丢了 dora 上下文**——整个节点要从 `main()` 重新初始化：重新反序列化 16MB 引擎、重新 HTTP 查推流地址、重新打开相机。在高速行驶的卡车上，这是秒级的感知盲区。
4. 这个 150ms 甚至可能是**误报**：`start`/`end` 用的是 `std::chrono::system_clock`（[.cpp:643](src/Dedect/yolov5.cpp#L643)），**不是 `steady_clock`**。NTP 对时或系统时间跳变会让这个差值完全失真。

**面试官会怎么追问**：
- 「为什么用 `exit` 而不是 `std::abort`/返回错误码/降级跳过这一帧？」
- 「150ms 这个阈值怎么定的？你的 tick 是 20ms（50Hz），150ms 意味着连续丢了 7 帧——那为什么不是连续 7 帧超时才动作？」
- 「为什么用 `system_clock` 计时？」（**送分题，能立刻答出应该用 `steady_clock` 会加分**）

**正确做法**：连续 N 帧超时才触发；触发后不是退出，而是降低 tick 频率 / 跳过检测只推流（降级模式）/ 上报健康状态给整车，由整车决定是否重启。

### 6.2 【最高危】遮挡检测器 `process()` 全程持锁 —— 独立线程形同虚设

**代码位置**：[RobustOcclusionDetector.cpp:128-179](src/Occlusion/RobustOcclusionDetector.cpp#L128)

```cpp
std::lock_guard<std::mutex> lock(mutex_);   // 从这一行起持锁
// ... 中间夹着 Sobel、blur、threshold、cvtColor、inRange、
//     morphologyEx(MORPH_CLOSE, 9x9)、findContours、drawContours、countNonZero
return (occluded_pixels / total_area) * 100.0;   // 到函数返回才解锁
```

**问题**：`mutex_` 同时保护队列和算法状态，而 `process()` 从第 128 行开始一直到函数结束都在锁内——**包括所有图像处理重活**。而 `pushFrame()` 需要同一把锁：

```cpp
void pushFrame(const cv::Mat& frame_bgr) {
    std::lock_guard<std::mutex> lock(mutex_);   // ← 主线程会在这里阻塞
    ...
}
```

`pushFrame` 是**被主线程（dora event loop）直接调用**的（[Camera_dora_node.cpp:205](src/Camera_dora_node.cpp#L205)）。所以在 960×540（`scale_factor=0.5` 缩放后）上跑一次完整的 Sobel + 9×9 形态学闭运算 + 轮廓提取 + 全图 `countNonZero`，主线程就在这儿干等。

**后果**：
- 引入独立线程的收益被锁抵消，主线程实际被同步阻塞
- 主线程的阻塞时间直接吃掉 YOLO 的 20ms tick 预算
- **最坏情况**：如果遮挡处理耗时 > tick 周期，dora 的输入事件队列会持续积压

**面试官会怎么追问**：
- 「你为什么要给遮挡检测单独开线程？」（回答「卸载主线程」→ 追问「那主线程为什么还会被阻塞？」）
- 「怎么改？」（标准答案：**缩短临界区**——在锁内只做「取帧 + 更新累加器 + 弹出最旧帧」这三步 O(像素) 的算术，把 `morphologyEx`/`findContours` 等搬到锁外操作局部副本；或者干脆让工作线程自己在锁内只 pop 一帧，然后解锁做全部处理）
- 「`m_accumulated_mask` 是共享状态，不进锁怎么做？」（答案：`m_accumulated_mask` 只被工作线程读写，只要把 `m_mask_buffer` 的访问和累加操作保持在工作线程内，就根本不需要暴露给 `pushFrame`）

### 6.3 【高危】推流线程无退出路径 —— 关闭时死锁

**代码位置**：[UsbCameraStreamer.cpp:155-213](src/Push/UsbCameraStreamer.cpp#L155)

```cpp
void UsbCameraStreamer::streamingFunction() {
    ...
    while (true) {                                    // ← 无退出条件
        isStreaming = true;                           // ← 也在这里写（无锁！）
        {
            std::unique_lock<std::mutex> lock(_mutex);
            conv.wait(lock, [this] { return (!frame_queue_.empty() && isStreaming); });
            //                                              ▲
            //                    如果 isStreaming == false，谓词永远为 false → 永久阻塞
            if (!isStreaming || frame_queue_.empty()) continue;
            frame_to_push = frame_queue_.front();
            frame_queue_.pop();
        }
        ...
    }
}
```

**三重问题**：

1. **`while(true)` 没有退出条件**，唯一的 `break` 路径是被注释掉的 `else` 分支（[.cpp:204-208](src/Push/UsbCameraStreamer.cpp#L204)）。
2. **谓词自相矛盾**：谓词要求 `isStreaming == true` 才唤醒，但 `stopStreaming()` 恰恰是把 `isStreaming` 置为 `false`。所以调用 `stopStreaming()` 后线程会**永远卡在 `conv.wait()`**。
3. **`stopStreaming()` 紧接着 `join()`**（[.cpp:127-137](src/Push/UsbCameraStreamer.cpp#L127)）——**join 一个永不退出的线程 = 永久挂起**。

**更糟的是数据竞争**：`isStreaming` 是裸 `bool`，在 [.cpp:172](src/Push/UsbCameraStreamer.cpp#L172) 被工作线程无锁写、在 [.cpp:184](src/Push/UsbCameraStreamer.cpp#L184) 无锁读，同时又在线程函数内被写——而 `startStreaming()`/`stopStreaming()` 在锁内写它。这是标准的 **data race（UB）**。

**还有构造函数的问题**：`UsbCameraStreamer(...)` 第一件事是 `stopStreaming()`，而 `stopStreaming()` 读的 `isStreaming` **在构造函数初始化列表里没有被初始化**（[UsbCameraStreamer.h:41](include/Push/UsbCameraStreamer.h#L41) `bool isStreaming;` 无初值）——**读取未初始化的 bool 是 UB**，且这次 UB 发生在启动路径上。

**为什么现在没炸**：因为 `usb_front_stream_` 是 `new` 出来的**裸指针，从来没有被 `delete`**（[Camera_dora_node.cpp:188](src/Camera_dora_node.cpp#L188)，且 `~Camera_dora_node` 里没有 delete、没有 `stopStreaming`）。对象永远不会析构，`stopStreaming()`/`join()` 永远不会被调用，线程随着进程退出被强杀。**「不析构」意外地掩盖了「无法析构」的 bug。**

**面试官会怎么追问**：
- 「`UsbCameraStreamer` 为什么用裸指针 `new`？为什么不用 `unique_ptr`？」（→ RAII + 所有权表达）
- 「如果现在让你给它加一个正确的 `stop()`，你怎么写？」（正确答法：`isStreaming` 改 `std::atomic<bool>` 或统一在 `_mutex` 下访问；`notify_all()` 唤醒等待者；谓词改为 `return !frame_queue_.empty() || !isStreaming;`；循环体内 `if (!isStreaming) break;`）
- 「`isStreaming = true;` 写在 `while` 循环里第一行，这是干什么？」（这是个残留 bug——每次循环都重置，会让 `stopStreaming()` 的 false 被覆盖）

### 6.4 【高危】`init()` 失败静默继续 —— 空指针解引用崩溃

**代码位置**：[Camera_dora_node.cpp:116-198](src/Camera_dora_node.cpp#L116) 与 [run():642](src/Camera_dora_node.cpp#L642)

```cpp

    ...
    if (!engine_init(engine_path_)) {
        std::cerr << "engine init is failed" << std::endl;
```

**崩溃链路**：
1. `engine_init` 失败 → `context` 保持 `nullptr`、`host_input_data` 保持 `nullptr`、`host_output_prob` 保持 `nullptr`
2. 主循环照常进入，`cap_ >> frame_` 拿到帧
3. `CameraCallback` → `yolo_main(frame)` → `memcpy(host_input_data, blob.ptr<float>(), 4.9MB)` → **向空指针写入 4.9 MB → SIGSEGV**
4. 即使侥幸躲过 3（比如帧恰好为空），随后 `doInference(*context, ...)` 也会解引用空 `context`

**另一条崩溃链路（相机打不开）**：`cap_.open` 失败 → `cap_ >> frame_` 得到空 Mat → `CameraCallback` 中的 `cv::imshow("frame", frame)`（[.cpp:523](src/Camera_dora_node.cpp#L523)，**这行是激活的，不是注释**）对空 Mat 会抛 `cv::Exception`（`imshow` 内部有 `CV_Assert(!img.empty())`），而 `CameraCallback` 没有任何 `try/catch` → 异常穿透 `run()` → 穿透 `main()` → `std::terminate`。

**顺带一个大坑**：`cv::imshow` + `cv::waitKey(1)` 留在生产代码里，意味着**节点必须要有图形显示环境才能运行**。Jetson 部署通常是无 X11 的 headless 环境，一旦没有 `DISPLAY`，`imshow` 会抛 `cv::Exception`。同时 `waitKey(1)` 在 GTK/Qt 后端下会强制刷新一个 GUI 窗口，在 20ms tick 的实时循环里是纯浪费。

**面试官会怎么追问**：
- 「`init()` 为什么返回 `void`？」（→ 应该返回 `bool` 或抛异常；构造函数里做 `init_dora_context_from_env()` 也一样——构造失败无法感知）
- 「C++ 里构造函数失败怎么处理？」（标准答案：**构造函数不应该做可能失败的复杂初始化**，应该拆出一个 `bool init()`，或使用工厂函数返回 `std::optional<T>`/`std::unique_ptr<T>`）
- 「`cv::imshow` 为什么留在生产代码里？」

### 6.5 【高危】`lapjv` 里的 `system("pause")` 和 `exit(0)` —— 库代码杀进程

**代码位置**：[utils.cpp:289](src/Track/utils.cpp#L289) 与 [utils.cpp:369-372](src/Track/utils.cpp#L369)

```cpp
if (!extend_cost) {
    cout << "set extend_cost=True" << endl;
    system("pause");       // ← Windows 的 cmd 内建命令
    exit(0);               // ← 直接退出整个进程
}

int ret = lapjv_internal(n, cost_ptr, x_c, y_c);
if (ret != 0) {
    cout << "Calculate Wrong!" << endl;
    system("pause");
    exit(0);               // ← 匹配算法失败 = 整车感知节点退出
}
```

**问题**：
1. **这是从 Windows 移植过来的代码**（`system("pause")` 是 cmd.exe 的内建命令）。在 Linux/Jetson 上 `system("pause")` 会执行 `/bin/sh -c pause`，返回 `sh: 1: pause: not found`，**并不会暂停**——然后立刻执行 `exit(0)`。所谓的「暂停等用户确认」在目标平台上是**静默的立即退出**。
2. **库代码不应该调用 `exit()`**。`lapjv` 是纯算法库，它的失败处理策略由调用方决定，不该由它替整个进程做生死决定。
3. **`exit(0)` 返回的状态码是 0（成功）**，会误导上层监控/重启脚本认为节点是正常退出。
4. `exit(0)` 不展开栈，同样跳过所有析构。

**触发概率**：`extend_cost` 分支实际走不到（`linear_assignment` 传的是 `true`）；但 `lapjv_internal` 返回非 0 是**真实可触发的**——Jonker-Volgenant 算法在数值退化（`cost_t` 是 `float`，大量相同代价值）时可能返回非 0。在高速行驶时随机退出，是严重的功能安全风险。

**面试官会怎么追问**：
- 「如果 `lapjv` 失败了，你认为正确的处理是什么？」（答：跳过本帧的跟踪、保留上一帧轨迹、上报降级状态；绝不能退出）
- 「这段代码是怎么进到你们仓库的？」（诚实答：从开源 ByteTrack C++ 移植，移植时没有清理 Windows 依赖——**这个问题考察的是工程师对第三方代码的审查习惯**）
- 「`kalmanFilter.cpp:135` 也有一个 `exit(0)`，你知道吗？」（[kalmanFilter.cpp:133-136](src/Track/kalmanFilter.cpp#L133)：`gating_distance` 的 `only_position` 分支直接 `printf + exit(0)`）

### 6.6 【中高危】CPU 侧三份全帧拷贝 + 无计算/传输重叠

**代码位置**：[yolov5.cpp:637-644](src/Dedect/yolov5.cpp#L637) 与 [yolov5.cpp:507-513](src/Dedect/yolov5.cpp#L507)

```cpp
cv::Mat pr_img = preprocess_img(img, INPUT_W, INPUT_H);   // 拷贝 1：resize 到新 Mat + copyTo 到灰底 Mat
cv::Mat blob = cv::dnn::blobFromImage(pr_img, 1.0/255.0, cv::Size(INPUT_W, INPUT_H),
                                      cv::Scalar(), true, false);   // 拷贝 2：HWC→CHW + RGB 转换
memcpy(host_input_data, blob.ptr<float>(), 640*640*3*4);            // 拷贝 3：拷进 pinned buffer
```

**问题一：三份多余拷贝。** `preprocess_img` 内部先 `cv::resize` 到新 Mat，再 `copyTo` 到带灰底的 Mat（2 次分配 + 2 次写入），`blobFromImage` 再做一次全图遍历做通道重排和归一化，最后 `memcpy` 又整体搬 4.9 MB。**在一帧 1920×1080 的输入上，这三次遍历是纯 CPU 开销，而且完全串行。**

**问题二：没有计算/传输重叠。** `doInference` 是完整串行的：

```cpp
CUDA_CHECK(cudaMemcpyAsync(buffers[0], input, ..., cudaMemcpyHostToDevice, stream));
context.enqueue(batchSize, buffers, stream, nullptr);
CUDA_CHECK(cudaMemcpyAsync(output, buffers[1], ..., cudaMemcpyDeviceToHost, stream));
cudaStreamSynchronize(stream);      // ← CPU 在这里干等 GPU 干完
```

`cudaStreamSynchronize` 之后，CPU 才开始做 `nms()`（[yolov5.cpp:664](src/Dedect/yolov5.cpp#L664)）、画框、推流。**这段时间 GPU 100% 空闲**；反过来 GPU 推理时 CPU 也没在准备下一帧。单帧总时间 ≈ CPU预处理 + 传输 + 推理 + CPU后处理，四段全串行。

**优化方向（面试可展开的点）**：
- **双缓冲 + 双流 ping-pong**：`buffers[2][2]`，两条 `cudaStream_t`，帧 N 在推理时 CPU 准备帧 N+1，把流水线填满。前提是 `IExecutionContext` 不能跨线程/跨流并发——需要**两个 context**（`engine->createExecutionContext()` 可调多次，TRT 8 下每个 context 独立），或用 TRT 8.4+ 的 `enqueueV3` + `cudaEvent` 做依赖。
- **融合预处理**：把 letterbox + 归一化 + HWC→CHW 合到一起，直接写进 pinned buffer（`cv::Mat` 可以包住 `host_input_data` 做零拷贝 resize：`cv::Mat wrapped(640, 640, CV_32FC3, host_input_data)`），省掉 2 次遍历。
- **更进一步：`cudaMemcpy2DAsync`** 配合 padding 做 stride 感知的传输，或直接在 GPU 上做预处理（NPP / 自写 kernel），把 letterbox 也搬到 GPU。

**面试官会怎么追问**：
- 「一帧的延迟构成是多少？瓶颈在哪？」（能画出「CPU预处理 ‖ H2D ‖ 推理 ‖ D2H ‖ CPU后处理」这条串行链并指出 GPU 利用率低，是关键加分项）
- 「为什么用 `cudaMemcpyAsync` 还要 `cudaStreamSynchronize`？既然是同步的，用 `cudaMemcpy` 不行吗？」（答：`cudaMallocHost` 的 pinned buffer 让 async 拷贝真正异步，为将来双缓冲留了口子；且 pinned 内存即使同步拷贝也比 pageable 快）
- 「`host_input_data` 为什么是 `float*` 而不是 `uint8_t*`？」（答：pinned 内存必须让 GPU 直接 DMA，模型输入是 FP32/FP16 的 CHW 张量。顺带可提：如果引擎是 INT8/FP16 输入，这里还能省一半到四分之三的带宽）

### 6.7 【中危】输出 ID 恒为 `"test"` —— 下游无法区分目标

**代码位置**：[Camera_dora_node.cpp:468](src/Camera_dora_node.cpp#L468)

```cpp

    std::string target_uuid = "test";//this->generate_target_uuid();   // ← 硬编码
    j["objects"].push_back(json{
        {"id", target_uuid},
        ...
    });
}
```

**问题**：`generate_target_uuid()`（[.cpp:630-638](src/Camera_dora_node.cpp#L630)，基于 `libuuid` 的 `uuid_generate_random` + `uuid_unparse`）**被写好了但被注释掉了**，实际发布的每一条目标消息里 `id` 都是字面量 `"test"`。而 `CMakeLists.txt:12` 还在 `find_library(UUID_LIB uuid)` 并链接 libuuid。

**后果**：下游拿到 10 个目标，10 个的 `id` 都是 `"test"`，**无法做跨帧目标关联**（这恰恰是跟踪模块存在的意义）。而 `track_id` 明明已经在手边（[.cpp:290](src/Camera_dora_node.cpp#L290) `int track_id = strack.track_id;`）却没有被输出。

这大概率是**一次调试遗留**（为了快速联调下游而临时写死）。但它同时暴露了一个设计问题：即使恢复 `generate_target_uuid()` 也是错的——**每帧给同一个目标生成随机 UUID，等于每帧换一个 ID**，比 `"test"` 更糟。正确的做法是把 `strack.track_id` 转成稳定字符串（如 `"cam_front_" + std::to_string(track_id)`）。

**面试官会怎么追问**：
- 「这个 `"test"` 是调试遗留还是设计？」（诚实承认 + 说清正确做法，比辩解更好）
- 「`generate_target_uuid()` 恢复回来就对了吗？」
- 「为什么 `#include <uuid/uuid.h>` 却用不了？」（考察是否通读了自己改的代码）

### 6.8 【中危】跨模块二进制接口无长度校验 —— 缓冲区越界读

**代码位置**：[Camera_dora_node.cpp:557-577](src/Camera_dora_node.cpp#L557)、[580-628](src/Camera_dora_node.cpp#L580)

```cpp
void Camera_dora_node::VehicleStatusCallback(const char* data, int data_len) {
    const VehicleStat_h *cur_stat = reinterpret_cast<const VehicleStat_h *>(data);
    if(cur_stat != nullptr){                      // ← 永远为真（见下）
        vehicle_speed_    = static_cast<float>(cur_stat->VehicleSpeed);
        vehicle_steering_ = static_cast<float>(cur_stat->SteeringAngle);
    }
    else { std::cerr << "Invalid pointer: cur_stat is null." << std::endl; }
}
```

和：

```cpp
void Camera_dora_node::LidarStatusCallback(const char* data, int data_len, int lidar_id) {
    const SensorStatusCode *cur_stat = reinterpret_cast<const SensorStatusCode *>(data);
    bool current_is_ok = cur_stat->status;        // ← 先解引用，再判空
    ...
    if(cur_stat != nullptr){                      // ← 这个判空毫无意义
        switch(lidar_id) { ... }
    }
}
```

**四重问题**：

1. **`data_len` 参数被完全忽略**。没有 `if (data_len < sizeof(VehicleStat_h)) return;` 的校验。如果上游发来的消息短于结构体，`cur_stat->VehicleSpeed` 就是**越界读**。在 C++ 里这是 UB，在功能安全场景（车辆控制）里这是不可接受的。
2. **`if (cur_stat != nullptr)` 是无效检查**。`data` 来自 dora 的 `read_dora_input_data`，非空则 `cur_stat` 非空；`data` 为空则 `reinterpret_cast(nullptr)` 得到 nullptr——但 `LidarStatusCallback` 里**在判空之前就已经解引用了**（`cur_stat->status`）。判空写在解引用之后，等于没写。
3. **对齐风险**。`data` 是 dora 给的 `char*`，没有任何对齐保证。`VehicleStat_h` 含 `float` 成员（需 4 字节对齐）。在 ARM64 上未对齐访问通常能工作（但慢），在严格对齐平台上直接 SIGBUS。正确做法是 `memcpy` 到本地结构体，而不是 `reinterpret_cast` 后直接读。
4. **没有协议版本/魔数/大小校验**。结构体一旦增删字段，静默读错位。`msg.h` 里定义了 `#pragma pack(1)` 的 `VehicleStatus`（含 `header` 帧头字段，`HEADER_VehStatus` = 1001），但这个 callback 用的却是另一个**外部头文件** `VehicleStat_h`——**两套协议定义并存，没有任何一致性保证**。

**面试官会怎么追问**：
- 「`reinterpret_cast` 一个网络字节流到结构体，有什么风险？」（期望听到：长度、对齐、字节序、版本、`pack` 差异、strict aliasing）
- 「`VehicleStat_h` 里 `Soc`/`VehicleSpeed`/`SteeringAngle` 是 `float`，`ErrorCode`/`VehicleModle` 是 `uint8_t`，`is_Stop` 是 `bool`——这个结构体在发送端和接收端的 sizeof 一定一样吗？」（考察对 padding / 编译器差异 / `bool` 表示的敏感度）
- 「`data_len` 这个参数你都没用，为什么签名里有？」

## 附：面试自我陈述建议

如果要在简历/面试中用这个项目，建议按以下主线组织叙事，**每个点都能顶住 3 层追问**：

**主线一：TensorRT 工程化落地能力。**
从「原版 trtx 样例每帧 `cudaMalloc`」讲到自己改成「启动时一次性分配 + pinned memory + 复用 stream + 及时 `delete[]` 引擎 blob」，这是**可量化**的性能改进（可提前准备好优化前后的延迟数据）。

**主线二：GPU 后处理下沉。**
自研 TensorRT Plugin (`IPluginV2IOExt`) 把 YOLOv5 的 sigmoid 解码和 anchor 还原放进 CUDA kernel，用 `atomicAdd` 做无锁槽位分配。要能讲清 plugin 的 `serialize`/`deserialize`/`clone` 契约、`getOutputDimensions` 的静态形状声明、以及 `enqueue` 挂 stream 的顺序语义。

**主线三：多目标跟踪的整车集成。**
不只是「调了 ByteTrack」，而是讲清楚：为什么用两级关联（BYTE 论文的核心贡献）、卡尔曼的 8 维状态定义（x, y, a, h, vx, vy, va, vh）与 Cholesky 分解求解增益、以及**为了给下游输出类别信息而做的 IoU 反查**（并主动承认它的缺陷）。

**主线四：业务算法创新。**
阿克曼转向角 → 二次/三次曲线 ROI → `pointPolygonTest` 采样过滤。这是**别人简历上没有**的东西，也是最能体现「懂车」的地方。

**必须主动承认的短板（面试官一定会发现，主动说比被问出来好）：**
1. `exit(1)` / `system("pause")` 这类进程级错误处理
2. `UsbCameraStreamer` 的线程退出路径缺失
3. 输出 ID 写成 `"test"` 的调试遗留
4. 单线程串行的推理流水线（没有 double-buffering）

**准备好被问的开放题：**
- 「这条流水线的延迟是多少？怎么测的？瓶颈在哪？」
- 「如果相机帧率从 30 fps 突然变成 60 fps，会发生什么？」（答案要提：dora tick 是 20ms/50Hz，`cap_ >>` 会阻塞；帧队列有界丢最旧所以不会 OOM，但主线程被拉满，`exit(1)` 看门狗会被触发 → **节点重启**）
- 「这套代码部署到 100 台车上，你怎么做版本管理和引擎分发？」（考察工程化思维：`.engine` 与 TRT 版本/GPU 架构强绑定，必须纳入 CI 按目标平台构建，不能进 git 仓库）
